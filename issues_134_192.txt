=== #189 Static review: directory validation reopens scanned paths and is vulnerable to file/symlink replacement TOCTOU ===

- root-relative descriptor traversal with no-follow semantics;

- detect inode/device replacement across any multi-pass operation;

Do not rely on a pathname-level precheck followed by a later pathname reopen.

Keep Swift/reference-validator semantics aligned where applicable.

## Acceptance

- a test/harness that swaps regular file -> symlink between metadata scan and hash fails closed;
- same-size regular-file replacement is detected or excluded by the snapshot/descriptor model;
- ordinary valid directories still validate;

=== #161 Static review: End RoomPlan transaction rollback is unsafe under actor reentrancy ===

- serialize the entire logical transaction without actor reentrancy across its commit window;

Do not remove an existing byte-identical canonical file merely because the current attempt failed.

- two overlapping identical End transactions cannot delete each other's committed bytes;
- conflicting transactions fail closed;
- failure after a subset of writes leaves either the prior committed transaction or a clean uncommitted state;

```swift
emitCurrentThermalState()
sampleStorage()
```

After that, storage has no notification-driven update and the monitor has no timer/polling loop.

The host explicitly samples again only at finalization, and `prepareEndScan()` performs a separate one-shot capacity query when the user presses End.

Therefore a long-running scan can cross:

- the 2 GiB warning threshold;
- then the 512 MiB critical threshold;

without producing a storage-pressure event while scanning.

Manual evidence writes, previews, RoomPlan state and other processes can consume storage during that interval. The first visible symptom may instead be a write failure or a late End-time rejection.

## Contract mismatch

The Phase 1 architecture calls for explicit storage/resource monitoring and persistence backpressure during capture, not only at startup/end.

## Required correction

Add bounded ongoing storage assessment while the resource monitor is active.

Possible implementation:

- periodic low-frequency sampling (for example every several seconds), or sampling tied to persisted-byte growth;
- emit only threshold transitions / meaningful changes to avoid flooding `resourceEvents`;
- use hysteresis so capacity oscillation near a boundary does not spam warnings;
- critical threshold must apply the existing capture failure/recovery policy promptly;
- cancel sampling on monitor stop/reset/finalization.

Keep the explicit final preflight storage assessment; periodic monitoring does not replace it.

## Acceptance

- crossing warning threshold during an active scan is detected before End;
- crossing critical threshold during an active scan invokes the existing critical-storage policy;
- no unbounded duplicate resource-event growth;
- monitor stop cancels future samples;
- tests use an injectable capacity source/clock rather than waiting in real time;
- RDC 0.

## Context

Capture Bundle v1 states that HTDT-Capture-owned JSON strings and keys must be NFC-normalized.

=== #138 Static review: annotation and measurement authority are not persisted as one recoverable transaction ===
## Context

Second-pass Review/Annotation persistence review of current `main` `0b976b98245bcc40a36e34755370130627b7ac4c`.

Related issues #110/#111 cover async stale-status and Save/Cancel races. This issue is specifically the two-file canonical persistence transaction.

No RDC was used.

## Finding

`commitAnnotationAuthority()` performs:

```swift
try await store.persistAnnotationPackage(annotationPackage)
try await store.persistMeasurementPackage(measurementPackage)
```

as two independent canonical commits.

`persistAnnotationPackage` writes/registers `annotations/entities.json` and mutates in-memory annotation authority before measurement persistence begins.

If measurement persistence then fails:

- annotation authority has already been committed to the working set;
- measurement authority is absent;
- the host catches the error and calls terminal `fail(.persistenceFailure)`;
- an otherwise accepted RoomPlan/frame/depth capture is lost from the normal workflow because the second half of an optional annotation save failed.

There is no exact-byte rollback of the first half and no atomic combined store operation.

## Impact

A recoverable filesystem/write failure while saving measurements can convert a valid accepted capture into terminal failure and leave a partial annotation transaction until failed-revision cleanup occurs.

The UI footer also says "Save writes the canonical annotation and measurement collections once", implying one logical commit.

## Required correction

Implement one store-level annotation+measurement transaction:

- validate both packages and authority compatibility before writing either;
- persist with byte-identical/idempotent semantics where appropriate;
- commit declarations/in-memory authority only after both files are durable;
- on rollback-safe failure, remove only bytes owned by that attempt using exact-byte checks;
- keep the accepted capture and annotation editor/review recoverable for retry;
- retain fail-closed behavior for true conflicting canonical authority/corruption.

Coordinate with #111 so Save/Cancel cannot race the transaction.

## Acceptance

- both files succeed -> one canonical commit;
- second-file write failure -> first-file attempt is safely rolled back and the capture remains recoverable;
- conflicting pre-existing canonical bytes fail closed;
- no partial declarations/in-memory authority survive a failed recoverable transaction;
- RDC 0.

=== #137 Static review: process death leaves orphan working revisions with no startup cleanup policy ===
## Context

Second-pass lifecycle/privacy review of current `main` `0b976b98245bcc40a36e34755370130627b7ac4c`.

Related: #129 tracks rediscovery of successfully finalized/exported captures. This issue concerns **incomplete working revisions**.

No RDC was used.

## Finding

The host deletes an incomplete working revision only through the in-process Failed -> Reset path:

`CaptureWorkingSetStore.discardIncompleteRevision()`.

If the process is terminated, crashes, or is killed by the OS while a revision exists under:

`HTDTCapture/working/<capture_revision_id>`

there is no startup inventory or cleanup policy for that working directory.

`HTDTCaptureHostCoordinator.init()` initializes fresh in-memory state/capability data and does not inspect prior working revisions.

The old live AR coordinate authority cannot safely be resumed after process death, so these stale working revisions are not usable as an active capture; they simply remain on disk.

## Impact

- sensitive partial room imagery/geometry can accumulate indefinitely;
- abandoned revisions consume storage;
- stale `.tmp-*` or partially persisted evidence can also remain after process death;
- the app provides no visibility or deletion path for these orphaned working sets.

This is not a request to resume the old ARSession/world frame.

## Required correction

Add a startup abandoned-working-revision policy.

A safe default is:

1. enumerate only app-owned `HTDTCapture/working/<uuid>` children;
2. positively distinguish the currently active revision (none at cold launch);
3. treat prior-process working revisions as non-resumable unless a future authority design explicitly proves continuity;
4. expose/delete them through a bounded safe cleanup transaction;
5. never delete outside the exact app-owned working root;
6. report cleanup failure and retained byte usage rather than silently ignoring it.

Consider removing abandoned writer temp files as part of the same policy.

## Acceptance

- terminate with an incomplete working revision -> relaunch -> the stale working data is deterministically surfaced/cleaned according to policy;
- no old coordinate-space authority is silently resumed;
- malformed/unexpected directories are not recursively deleted without ownership proof;
- cleanup failures remain visible/retryable;
- RDC 0 for implementation.

=== #135 Static review: bundle validators hash schema-owned JSON without validating its schema ===
## Context

Second-pass Capture Bundle v1 / ingestion-boundary review of current `main` `0b976b98245bcc40a36e34755370130627b7ac4c`.

No RDC was used.

## Finding

The repository publishes JSON Schemas for HTDT-Capture-owned payloads:

- session;
- device;
- capabilities;
- capture configuration;
- timing;
- frame descriptors;
- mesh anchors;
- annotations;
- measurements;
- quality.

The schema README states that the reference bundle validator **additionally** enforces constraints that JSON Schema cannot safely express alone.

But both validation authorities currently stop at manifest structure + file integrity:

- Swift `BundleDirectoryValidator` decodes/canonicalizes the manifest, then checks declared paths, lengths and SHA-256.
- Python `tools/bundle_validator/validator.py` validates manifest shape/canonicality, then checks declared paths, lengths and SHA-256.

Neither validator applies the published payload schemas to declared schema-owned JSON files.

Thus a bundle can contain, for example, a hash-correct `quality/capture-quality.json` or `session/capture-session.json` with structurally invalid contents and still receive `valid: true` from the Capture Bundle validator.

The reference ingestor validates only selected payload semantics later (notably mesh/annotation/measurement) and does not make the bundle validator's `valid` result equivalent to full schema validity.

## Contract mismatch

`docs/HTDT_INGESTION_CONTRACT.md` defines the import sequence as:

```
archive safety validation
-> manifest/schema validation
-> payload length/hash validation
-> ...
```

and states that invalid identity/coordinate references fail closed before source promotion.

The current bundle-validation boundary does not actually enforce all published payload schemas.

## Impact

- malformed schema-owned canonical records can be accepted as a valid Capture Bundle;
- native untrusted archive import can promote such a directory because it relies on bundle validation;
- downstream components must rediscover malformed semantics independently;
- the meaning of "validated bundle" is weaker than the documented ingestion boundary.

## Required correction

Define and enforce a path -> schema mapping for HTDT-Capture-owned JSON payloads and validate them as part of the bundle validation transaction.

At minimum cover the fixed v1 paths and patterned frame descriptors.

Keep non-HTDT opaque Apple/raw artifacts out of this mapping unless they have an explicit project-owned schema.

Swift and Python validation semantics must match.

Do not remove the existing canonical-manifest, path-safety, byte-length or hash checks; schema validation is additional.

## Acceptance

- hash-correct but schema-invalid session/frame/mesh/annotation/measurement/quality payloads fail bundle validation;
- valid frozen fixtures still pass;
- directory and archive wrappers behave equivalently;
- native import cannot promote schema-invalid HTDT-owned JSON;
- RDC 0.
